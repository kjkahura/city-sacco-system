# Webhooks Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Webhooks after the reference platform. A template names an event, conditions, a body with placeholders and an HTTPS endpoint. Events are captured with the change that raises them, delivered with retries, logged, and can be resent.

**Architecture:**
- Triggers in tenant migration 045 write events to an outbox, `notification_events`, in the same transaction as the change, and only when an active template wants the event.
- A dispatcher (`src/domain/notifications/`) turns events into messages and delivers them. It runs:
  - after write requests;
  - from `cli notifications:run`, the in-process scheduler and the `sacco-notify` Cloud Run job.
- Requests go out through `src/lib/outbound.js`, the backup callback's address guard made shared.

**Tech Stack:** Node 22 CommonJS, Express 5, Postgres 16 (plpgsql triggers), node `https`, plain ES modules in the console.

**Spec:** `platform/docs/audits/audit-webhooks.md`. John accepted all 11 decision defaults on 4 October 2026, with signing on by default and HTTPS only.

## Global Constraints

- **Vendor name:** never in code, docs, commit messages or paths; it is "the reference platform".
- **Writing style:** plain factual prose, no em dashes.
- **Running products:** existing behaviour is unchanged when no template exists. Triggers write nothing then.
- **Delivery:** only `2xx` is delivered. Requests time out after 10 s and follow no redirects. URLs are HTTPS only, except with `CALLBACK_ALLOW_PRIVATE=true`, which is for development and tests.
- **Retry schedule:** retries wait 1, 5, 15 and 60 minutes, then 3, 6, 9, 12, 15, 18, 21 and 24 hours from the first try. That is 9 retries in all, then `FAILED`.
- **Circuit breaker:** after 20 consecutive failures, a template's messages wait (`WAIT_FOR_CLOSE_CIRCUIT`). One message is tried every 10 minutes, and a success closes the circuit.
- **Body limits:**
  - a body is at most 65,536 bytes, otherwise `MAX_MESSAGE_SIZE_LIMIT_EXCEEDED`;
  - message bodies are cleared after 180 days, and the rest of the log is kept.
- **Idempotency header:** `x-notifications-idempotency-key`. It is the same on retries and new on a manual resend.
- **Signature header:** `x-sacco-signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<body>">`, with a per-template secret. It is on by default.
- **Secrets:**
  - basic authentication passwords and signing secrets are stored AES-256-GCM encrypted, under `SECRETS_KEY` or, failing that, a key derived from `JWT_SECRET`;
  - they are never returned, except the signing secret once when it is created or rotated.
- **Permissions:**
  - new codes: VIEW_COMMUNICATION_HISTORY (MANAGER, AUDITOR) and RESEND_FAILED_MESSAGES (MANAGER);
  - templates use CREATE_ and EDIT_COMMUNICATION_TEMPLATES;
  - the tenant-wide switch is for administrators only.
- **Commits:** as John, with the session trailers, staged by path.

## Review Focus

1. **A member name with a quotation mark or a newline in a JSON body.** The rendered body must still be valid JSON.
2. **A posting reversed in the same request that raised it.** Both events must be delivered, in order of creation.
3. **Two dispatchers running at once.** This happens when the job and the post-request run overlap. No message may be sent twice by them; rows are claimed with `SKIP LOCKED`.
4. **A template deactivated while messages are queued.** Queued messages may still go, as on the reference platform, but no new events are raised.
5. **A receiver that redirects (`3xx`) or answers slowly.** That is a failure with a reason, never a hang.

### Task 4: Dispatcher and sender

**Files:**
- Create: `src/domain/notifications/dispatch.js`, `src/domain/notifications/render.js`, `src/domain/notifications/context.js`.
- Modify: `bin/cli.js` (`notifications:run`), `src/ops/scheduler.js` (every minute), `src/server.js` (a run after write requests, debounced per tenant, only when the tenant has an active template).

`runTenant(schema)`:
1. Claim unprocessed events with `FOR UPDATE SKIP LOCKED`.
2. For each matching activated template, build the context, check the conditions, render the body and queue a message.
3. Send the messages that are due, oldest first, with:
   - the 2xx rule;
   - the idempotency key, the signature and basic authentication;
   - the retry schedule and the circuit breaker;
   - the switch (`WEBHOOK_NOTIFICATIONS_DISABLED`).
4. Once per organization day, raise REPAYMENT_REMINDER for installments due in `triggerDays` days.
5. Clear bodies older than 180 days.

Placeholders:
- CLIENT_NAME, CLIENT_ID, CLIENT_KEY, FIRST_NAME, MIDDLE_NAME, LAST_NAME, GROUP_NAME, MOBILE_PHONE, EMAIL_ADDRESS, BRANCH_NAME;
- ACCOUNT_ID, ACCOUNT_KEY, ACCOUNT_NAME, ACCOUNT_STATE, PRODUCT_NAME, TOTAL_BALANCE, AVAILABLE_BALANCE;
- TRANSACTION_ID, TRANSACTION_KEY, TRANSACTION_TYPE, TRANSACTION_AMOUNT, TRANSACTION_VALUE_DATE, REVERSAL_OF;
- LOAN_AMOUNT, PRINCIPAL_BALANCE, INTEREST_RATE, DISBURSEMENT_DATE, INSTALLMENT_NUMBER, INSTALLMENT_DUE_DATE, INSTALLMENT_DUE_AMOUNT, PRINCIPAL_DUE, INTEREST_DUE;
- CREDIT_ARRANGEMENT_ID, JOURNAL_ENTRY_ID, ACTIVITY_TYPE, EVENT, ORGANIZATION_NAME, CURRENCY_CODE, CURRENT_DATE, SYSTEM_DATE;
- custom fields of the main record, by field ID.

For a JSON body, values are escaped as JSON string content. Conditions take a placeholder name or custom field ID, with EQUALS, DIFFERENT_THAN, MORE_THAN, LESS_THAN, BETWEEN, IN, STARTS_WITH, EMPTY or NOT_EMPTY, joined by MATCH_ALL or MATCH_ANY.
